# Learning Plan: AWS with CDK

A phased roadmap for building the e-commerce platform from an empty account to a
production-shaped architecture. Each phase delivers working, tested infrastructure — nothing is a
demo that gets thrown away, and each phase assumes the ones before it exist.

```
Phase 1   Networking                     ✅ done
Phase 2   Compute & Containers           ✅ done
Phase 3   Database & Persistence         ✅ done
Phase 3.5 TLS & DNS                      ✅ done
Phase 4   Authentication & Authorization ✅ done
Phase 5   Messaging & Event-Driven       ← next
Phase 6   Caching & Performance
Phase 7   Observability & Security
Phase 8   CI/CD
Phase 9   Production Architecture
```

Two rules apply to every phase:

- **Baseline observability is woven in, not deferred.** Every new component ships with at least
  one CloudWatch alarm the day it lands. Phase 7 is the deep dive, not the first time the platform
  gets eyes.
- **Nothing already built needs redesigning to land a later phase.** Subnets, security groups,
  tags, IAM split and exports are the contract; a new phase consumes them.

---

## Phase 1 — Networking ✅

**Delivered:** VPC with public / private-with-egress / isolated subnets across AZs (2 dev/uat, 3
prod), Internet Gateway, NAT Gateways (1/2/3), three-tier security group model (ALB → App → DB by
reference, `allowAllOutbound: false`), optional VPC Flow Logs, restricted default security group,
environment-scoped exports.

**Concepts:** CIDR, subnets, route tables, IGW vs NAT, security group references, per-AZ blast
radius, `Fn::GetAZs` vs `maxAzs`.

## Phase 2 — Compute & Containers ✅

**Delivered:** ECR repository (scan-on-push, untagged expiry), ECS Fargate cluster + service,
internet-facing ALB on port 80, `/actuator/health` target-group checks, deployment circuit breaker
with rollback, CloudWatch log group. Spring Boot API packaged as a multi-stage, non-root image.
Scoped execution role; permissionless task role.

**Concepts:** ECS vs Fargate vs EC2 launch type, task definitions, target groups, health checks,
execution vs task IAM role, immutable image tags.

## Phase 3 — Database & Persistence ✅

**Delivered:** RDS PostgreSQL 16 in isolated subnets (no route off the VPC), gp3 encrypted storage,
automated backups (1/7/30 days), Multi-AZ in prod only, deletion protection + `RETAIN` in uat/prod.
Credentials generated by Secrets Manager and injected by ECS; never present in code, template or
image. Flyway owns the schema; Hibernate validates.

**Concepts:** isolated subnets, DB subnet groups, dynamic references, secret injection vs env vars,
deletion protection vs removal policy, point-in-time recovery.

## Phase 3.5 — TLS & DNS ✅

Small phase, deliberately pulled ahead of auth: bearer tokens must never travel in plaintext.

**Delivered:** Route 53 public hosted zone for the delegated subdomain (created, never looked up),
ACM certificate for `api.<env-domain>` validated by DNS against that zone, HTTPS listener on 443
(TLS 1.2 floor) forwarding to the existing target group, port 80 listener as a permanent redirect,
alias `A` record to the ALB, and an `ecommerce-dns-<env>` stack between the database and the
application. Prod fails validation without a domain; dev/uat still synthesise HTTP-only. No new IAM,
no new security group rule (Phase 1 already opened 443).

**Acceptance:** `curl -I http://…` returns a 301 with `Location: https://…`;
`https://<domain>/actuator/health` answers `{"status":"UP"}`; no plaintext path remains.

**Concepts:** DNS delegation and NS records, DNS vs email validation, certificate lifecycle and
renewal, listener actions vs target groups, redirect actions, alias records vs IP addresses.

## Phase 4 — Authentication & Authorization ✅

**Delivered:** a Cognito user pool (`ecommerce-cognito-<env>`) with a **confidential** app client and
a client secret in Secrets Manager, and a Spring Boot API that is the OAuth client — the **Backend
for Frontend** pattern. The browser holds only an `httpOnly`, `Secure`, `SameSite=Lax` session
cookie; the app runs the **authorization code + PKCE** flow server side and holds the tokens itself.
Only the authorization code flow is enabled: no implicit flow, no client credentials, and no resource
owner password grant (RFC 9700 deprecates it, so `ALLOW_USER_PASSWORD_AUTH` never appears). `state`
and `nonce` stay on. Logout is RP-initiated and the refresh token rotates and is revoked.

`cognito:groups` is mapped to `ROLE_<group>` authorities, and one `SecurityConfig` expresses the
whole policy: `GET /api/**` and `/actuator/health` are public, writes under `/api/**` require the
`admin` group, everything else is authenticated, and an unauthenticated `/api/**` call answers `401`
rather than redirecting. CSRF stays on with Spring Security's SPA handling; CORS allows only exact
configured origins with credentials.

**Deliberately deferred:** bearer-token / resource-server support for future mobile or service
clients (`spring-boot-starter-oauth2-resource-server` is not on the classpath), and orders — Phase 5
owns the order domain and inherits the same authorization rule.

**Known constraint:** sessions are in memory, so `application.desiredCount > 1` is rejected at synth
until sessions move to Redis (Phase 6).

**Acceptance:** unauthenticated `GET /api/products` → 200; unauthenticated `POST` → 401; authenticated
non-admin `POST` → 403; admin `POST` → 201 with the row persisted; `/actuator/health` → 200
unauthenticated. Enforced by claim, never by endpoint secrecy.

**Concepts:** user pools vs identity pools, BFF vs SPA-held tokens, OIDC auth-code + PKCE,
confidential vs public clients, claim-to-authority mapping, CSRF for SPAs, session cookies and
`SameSite`, RP-initiated logout and token rotation, why ALB `authenticate-oidc` is not enough.

## Phase 5 — Messaging & Event-Driven ⬜

**Scenario:** order pipeline — the first real async flow.

```
POST /api/orders → RDS write + publish OrderPlaced → SNS
                                                    │
                                    SQS (order-processing) + DLQ
                                                    │
                                    worker (Lambda or second Fargate service)
                                                    │
                                    order status → confirmed / failed
```

**Scope:**

- SNS topic `order-events`; SQS queue subscribed, with a redrive policy into a DLQ.
- Worker consumes, processes idempotently, updates order status in RDS.
- The task role finally earns permissions: scoped `sqs:`/`sns:` grants (the first non-empty task
  role is a milestone).
- EventBridge scheduled job (e.g. nightly abandoned-order sweep) as the scheduled-event pattern.

**Acceptance:** publish survives API restart; a poisoned message lands in the DLQ after N retries;
re-delivery does not double-process (idempotency key).

**Concepts:** SNS vs SQS vs EventBridge, fan-out, DLQs, visibility timeout, at-least-once
delivery, idempotent consumers, event schema discipline.

## Phase 6 — Caching & Performance ⬜

**Scope:**

- ElastiCache (Redis) in the private subnets, behind a cache security group — same pattern as the
  database tier. Cache-aside on `GET /api/products`.
- **ECS service auto scaling** — the explicit home for closing the `desiredCount = 1` gap:
  target tracking on CPU (and request count), min 2 / max N in prod. This is the change that makes
  an AZ or task loss a non-event.
- CloudFront distribution in front of the ALB: caching behaviours for cacheable product reads,
  TLS at the edge.
- Optional: DynamoDB for cart/session data — the key-value contrast to the relational model.

**Acceptance:** repeat product reads hit Redis (measurable latency drop / DB query absence);
scale-out fires under synthetic load and the service stays healthy; CloudFront serves cached
responses with correct TTLs.

**Concepts:** cache-aside vs write-through, TTL and invalidation, target-tracking vs step scaling,
CloudFront behaviours and origin security (OAC/custom headers).

## Phase 7 — Observability & Security ⬜

The deep dive; baseline alarms have been landing with each phase since Phase 4.

**Scope:**

- CloudWatch dashboard: ALB 5xx/latency, ECS CPU/memory + running task count, RDS
  connections/CPU/storage, queue depth, DLQ messages.
- Alarm fan-out → SNS → email/chat. Synthetics canary hitting the health endpoint.
- Tracing: ADOT/X-Ray instrumentation of the API; trace the full request path ALB → app → RDS →
  cache → queue.
- Security: WAF web ACL on the ALB/CloudFront (managed rules + rate limiting), cdk-nag
  `AwsSolutionsChecks` in the test suite, Secrets Manager rotation for the RDS credential,
  GuardDuty + Security Hub, IAM Access Analyzer.
- VPC endpoints (gateway S3, interface ECR/Secrets Manager) — removes AWS-API traffic from the
  NAT path, cuts NAT cost, tightens egress.

**Acceptance:** one dashboard shows the whole platform; a simulated fault (kill a task, fill the
DLQ, spike 5xx) produces an alarm and a traceable diagnosis; cdk-nag runs clean or with justified
suppressions.

## Phase 8 — CI/CD ⬜

Replaces today's manual `docker build`/`push`/`cdk deploy` entirely.

**Scope:**

- Pipeline: GitHub Actions + OIDC (no static AWS keys) **or** CDK Pipelines — pick one, do it
  properly.
- Stages: lint → `npm test` + `mvn test` → `cdk synth --strict` → build/push image with an
  immutable tag → `cdk diff` gate → deploy dev → uat → prod behind manual approval.
- Post-deploy integration tests (the README's curl checks, automated) against the deployed dev
  environment.
- `cdk drift --fail` as a scheduled job.

**Acceptance:** a merge to main lands in dev with no human step, promotes to prod with one
approval; a failing post-deploy test blocks promotion; drift fires a notification.

**Concepts:** OIDC federation, environment protection rules, self-mutating pipelines (if CDK
Pipelines), image tag immutability in the pipeline context, drift-aware change sets.

## Phase 9 — Production Architecture ⬜

**Scope:**

- Multi-account structure via AWS Organizations (dev/uat/prod accounts); the per-env
  `ECOMMERCE_<ENV>_ACCOUNT` pins become real account ids.
- DR posture: cross-region backup copy for RDS, a restore drill (actually restore and verify),
  documented RTO/RPO.
- Multi-AZ failover test on the prod database; AZ-loss game day for ECS.
- Cost guardrails: budgets + cost anomaly detection, tagged-cost reports.
- Runbooks for the known failure modes (task won't start, DLQ accumulating, RDS failover, cert
  expiry).

**Acceptance:** a prod database failover completes inside the RTO with no data loss; a restored
backup passes the API smoke test; a monthly cost report by `Environment` tag exists.

**Concepts:** Organizations/SCPs, cross-region backup, failover vs read replica, game days,
cost allocation, operational readiness review.

---

## Deferred / explicitly out of scope

- API Gateway + Lambda variant of the API (worth a spike once the ALB path is boring).
- ECS blue/green or CodeDeploy canary deployments.
- Customer-managed KMS keys — belongs in the Phase 7 hardening pass if it lands at all.
- Multi-*region* active-active — out of scope; Phase 9 covers backup/restore DR only.
- Service discovery/App Mesh, EKS — deliberate non-goals for this learning path.
